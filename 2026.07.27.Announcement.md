# CoreDesign, July 27 2026: Sample Moves to PostgreSQL, and a Breaking Change in CoreDesign.Data

I'm pushing out a change to the Sample application and a new version of `CoreDesign.Data` today. The two are related: converting Sample surfaced a real gap in how `CoreDesign.Data` handled dates, and fixing it properly turned into a breaking change worth its own announcement.

## Why Sample moved off SQL Server

The Sample solution's Aspire AppHost previously provisioned a SQL Server container for local development. SQL Server's Docker image is large, multiple gigabytes, which adds real time to the first `docker pull` anyone does when they clone the repo and spin up the stack for the first time. PostgreSQL's image is a fraction of the size and starts faster, with no loss of functionality for what Sample demonstrates.

To be clear about what this does and doesn't mean: `CoreDesign.Data` was already database-engine agnostic before this change, it's built on EF Core's provider model, and nothing about its public API assumes SQL Server. Sample moving to PostgreSQL is a demonstration that the switch is genuinely just a provider swap (`UseSqlServer` to `UseNpgsql`, an updated connection string, new EF Core migrations generated the normal way), not a signal that SQL Server support is going away or was ever a special case. Both remain fully supported.

## The bug the conversion found

Converting Sample's database provider is exactly the kind of change that exercises code paths SQL Server never stressed. In this case: Npgsql maps `DateTime` to PostgreSQL's `timestamp with time zone` column type, and it strictly rejects writing any `DateTime` whose `Kind` is `Local` or `Unspecified`. SQL Server's `datetime2` never validated `Kind` at all, so a `DateTime` that wasn't explicitly UTC would silently work against SQL Server and throw against PostgreSQL.

My first fix was narrow: add a UTC-normalizing conversion to `BaseEntity`'s `CreatedAt` and `UpdatedAt` properties, since those are the two `DateTime` fields every CoreDesign.Data entity has by default. That fixed Sample. It did not fix the general problem: any application-defined entity with its own `DateTime` property, outside of `BaseEntity`, was still exposed to the exact same failure the moment it received a non-UTC value.

## The actual fix: a model-wide convention

`CoreDesign.Data` 1.2.0 replaces the narrow, per-property fix with a model-wide EF Core convention. `CoreDesignDbContext`, the base class every CoreDesign.Data-backed `DbContext` already derives from, now registers the UTC conversion in `ConfigureConventions`. Every `DateTime` and `DateTime?` property on every entity in your model gets normalized to UTC on write and stamped `Kind=Utc` on read, automatically, with no per-entity opt-in required.

This is the correct scope for what "cross-database compatibility" should mean in a data access library: a policy like this shouldn't depend on every entity author remembering to wire it up correctly. It's also less code long-term, one registration in the base context instead of repeating a `.HasConversion(...)` call on every `DateTime` property, forever, in every entity configuration.

**This is a breaking change.** Any application with its own `DateTime` entity properties, including ones that previously carried a manual `DateTime.SpecifyKind`-style workaround, will see those properties' values normalized to UTC that previously weren't. Full upgrade instructions, including how to identify affected properties and what to remove, are in [CoreDesign.Data.1.1.2-to-1.2.0-migration.md](CoreDesign.Data.1.1.2-to-1.2.0-migration.md). No EF Core migration is required, this only changes how .NET reads and writes the value at the driver boundary, not the column's store type.
