# CoreDesign.Logging: Migrating from 1.0.5 to 1.1.0

## Overview

Version 1.1.0 introduces a Roslyn source generator as the primary way to add structured logging to any service. Placing `[LoggingDecorator]` on an interface produces a complete, compile-time decorator class. The old `DispatchProxy` proxy middleware remains in the package and works without modification, so migration is optional and can be done incrementally.

The source generator approach offers three concrete improvements over the proxy:

- **AOT compatible.** No `DispatchProxy`, no `MethodInfo.Invoke`, no `MakeGenericMethod`. Generated code is plain C# that the native AOT compiler can handle.
- **Direct method calls.** No reflection overhead on every invocation.
- **Compile-time safety.** A missing or mismatched method on the decorator is a build error, not a silent runtime gap.

---

## Before You Begin

Update the NuGet package reference to 1.1.0:

```xml
<PackageReference Include="CoreDesign.Logging" Version="1.1.0" />
```

Or via the CLI:

```
dotnet add package CoreDesign.Logging --version 1.1.0
```

The generator ships inside the package as a Roslyn analyzer. No additional project reference is needed.

## Migration Steps

### Step 1: Add `[LoggingDecorator]` to Each Interface

For every class that previously implemented `ILoggable`, move the opt-in from the implementation to its interface. The attribute goes on the interface, not the class.

**Before (1.0.5)**

```csharp
// Interface — no attribute
public interface ICreateForecastHandler
{
    Task<OneOf<WeatherForecast, BadRequestMessage>> CreateAsync(
        Request request, Guid userId, CancellationToken ct);
}

// Implementation — carries ILoggable
public class CreateForecastHandler(...) : ICreateForecastHandler, ILoggable
{
    public async Task<OneOf<WeatherForecast, BadRequestMessage>> CreateAsync(
        Request request, Guid userId, CancellationToken ct)
    {
        // ...
    }
}
```

**After (1.1.0)**

```csharp
// Interface — carries [LoggingDecorator]
[LoggingDecorator]
public interface ICreateForecastHandler
{
    Task<OneOf<WeatherForecast, BadRequestMessage>> CreateAsync(
        Request request, Guid userId, CancellationToken ct);
}

// Implementation — no ILoggable, no changes
public class CreateForecastHandler(...) : ICreateForecastHandler
{
    public async Task<OneOf<WeatherForecast, BadRequestMessage>> CreateAsync(
        Request request, Guid userId, CancellationToken ct)
    {
        // ...
    }
}
```

Repeat for every interface whose implementation previously carried `ILoggable`.

### Step 2: Remove `ILoggable` from Implementations

Once `[LoggingDecorator]` is on the interface, `ILoggable` on the implementation is no longer needed. Remove it from the class declaration.

### Step 3: Update DI Registration

Replace the assembly-scanning `AddWithLogging` call with individual `AddTransient` registrations followed by a single `DecorateWithLogging()` call.

**Before (1.0.5)**

```csharp
// Configuration.cs or equivalent infrastructure setup
services.AddWithLogging(typeof(Program).Assembly);
```

**After (1.1.0)**

```csharp
// ModuleConfig.cs or equivalent feature registration
services.AddTransient<ICreateForecastHandler, CreateForecastHandler>();
services.AddTransient<IGetAllForecastsHandler, GetAllForecastsHandler>();
services.AddTransient<IGetForecastHandler, GetForecastHandler>();
services.AddTransient<IUpdateForecastHandler, UpdateForecastHandler>();
services.AddTransient<IDeleteForecastHandler, DeleteForecastHandler>();

services.DecorateWithLogging();
```

`DecorateWithLogging()` is generated by the source generator. It wraps every interface in the project marked with `[LoggingDecorator]`. As new interfaces are marked, they are picked up automatically on the next build.

If your project uses explicit per-class `AddWithLogging<TInterface, TImpl>()` calls rather than assembly scanning, replace each one with the corresponding `AddTransient<TInterface, TImpl>()`:

```csharp
// Before
services.AddWithLogging<IWeatherForecastService, WeatherForecastService>();

// After
services.AddTransient<IWeatherForecastService, WeatherForecastService>();
// ... then call DecorateWithLogging() once after all registrations
services.DecorateWithLogging();
```

### Step 4: Replace `[TruncateLog]` with Serilog Destructure Configuration

`[TruncateLog]` is not supported by the generator. Move log output size control to the Serilog configuration in `appsettings.json`.

**Before (1.0.5)**

```csharp
// On the interface method
[TruncateLog(2000)]
Task<IReadOnlyList<WeatherForecast>> GetAllAsync(CancellationToken ct);
```

**After (1.1.0)**

Remove all `[TruncateLog]` attributes. Add a `Destructure` block to the `Serilog` section of `appsettings.json`:

```json
"Serilog": {
  "Destructure": [
    { "Name": "ToMaximumDepth", "Args": { "maximumDestructuringDepth": 5 } },
    { "Name": "ToMaximumStringLength", "Args": { "maximumStringLength": 500 } },
    { "Name": "ToMaximumCollectionCount", "Args": { "maximumCollectionCount": 10 } }
  ]
}
```

`ToMaximumDepth` is the most important setting. Without it, a deeply nested object graph such as an EF Core entity with navigation properties will cause Serilog to traverse every reference and stream an enormous payload into every sink. `ToMaximumStringLength` and `ToMaximumCollectionCount` cap string values and collection sizes respectively.

These limits apply uniformly to all handlers and all sinks. They can be overridden per environment in `appsettings.Development.json` or `appsettings.Production.json` without touching source code or rebuilding.

### Step 5: Delete Hand-Written Decorator Classes

If the project contains any decorator classes that were written by hand before the generator existed, they can be deleted. The generator now produces equivalent classes at compile time.

## Side-by-Side Comparison

### Registration

| 1.0.5 | 1.1.0 |
|---|---|
| `ILoggable` on the implementation class | `[LoggingDecorator]` on the interface |
| `services.AddWithLogging(assembly)` | `services.AddTransient<I, T>()` for each pair, then `services.DecorateWithLogging()` |
| `services.AddWithLogging<I, T>()` | `services.AddTransient<I, T>()`, then `services.DecorateWithLogging()` |

### Output Size Control

| 1.0.5 | 1.1.0 |
|---|---|
| `[TruncateLog(N)]` attribute on each interface method | `Serilog:Destructure` block in `appsettings.json` |
| Per-method, requires a code change to adjust | Per-environment, adjustable without a rebuild |
| Applies only to that method's return value | Applies uniformly to all log output across all handlers and sinks |

### Attributes That Remain Unchanged

`[Redact]` and `[Suppress]` work identically in both approaches. No changes needed.

```csharp
// Works the same with [LoggingDecorator] as it did with ILoggable
Task<LoginResult> LoginAsync(string username, [Redact] string password);

[Suppress]
Task<string> IssueTokenAsync(string userId);
```

## Staying on the Proxy

The proxy infrastructure is fully retained in 1.1.0. If you choose not to migrate, no changes are required. Classes with `ILoggable` and calls to `AddWithLogging` continue to work exactly as before.

You can also migrate incrementally: apply `[LoggingDecorator]` to some interfaces and leave others on `ILoggable`. Both can coexist in the same project. Call both `AddWithLogging(assembly)` and `DecorateWithLogging()` during startup while the transition is in progress.

The proxy remains the better choice when per-method `[TruncateLog]` granularity is specifically needed and migration to Serilog destructuring is not feasible.

## Troubleshooting

**`DecorateWithLogging()` is not found.**
The method is generated by the Roslyn analyzer. Ensure the project has built at least once after adding the `[LoggingDecorator]` attribute to an interface. If the error persists, check that the package version is 1.1.0 and that Roslyn analyzers are not suppressed in the `.csproj` file.

**The generated decorator class is not visible in the IDE.**
Generated files live in a virtual folder under `Dependencies > Analyzers` in Solution Explorer. They are not written to disk. This is normal behavior for Roslyn source generators.

**A method on the interface is not being logged.**
Verify that `[LoggingDecorator]` is on the interface, not the implementation class. The generator only processes interfaces. Also check that the method is not annotated with `[Suppress]`.

**Log output is not truncated.**
Ensure the `Serilog:Destructure` section is present in the effective `appsettings.json` for the running environment. When running under Aspire, the active environment is `Development`; the relevant file is `appsettings.Development.json` or whichever file takes precedence in the configuration chain.

**A `OneOf` arm is being logged at Information when Warning was expected.**
The generator determines log level from the arm's type name. Warning-level arms must have a type name containing `NotFound`, `BadRequest`, `Error`, `Failure`, `Unauthorized`, `Forbidden`, `Conflict`, or `InvalidOperation`. If a custom error type does not match any of these keywords, it will be logged at Information.
