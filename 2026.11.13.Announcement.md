# CoreDesign, November 13 2026: CoreDesign 10.0.1, Two Fixes for the .NET 10 Line

CoreDesign 10.0.1 is a patch release for the .NET 10 line. It fixes two bugs that turned up while verifying the source generators against an updated compiler, and the Sample application now runs on the 10.x packages. Every CoreDesign package moves to 10.0.1 together, and there are no API changes.

## DecorateWithLogging() now handles open generic registrations

`CoreDesign.Logging` has always generated decorators for generic interfaces. The docs promised that a single `DecorateWithLogging()` call covers every registration of such an interface. That held for closed registrations, but the most common way to register a generic repository is an open generic one:

```csharp
[LoggingDecorator]
public interface IRepository<T> where T : class
{
    Task<T?> GetByIdAsync(Guid id, CancellationToken ct);
}

services.AddScoped(typeof(IRepository<>), typeof(Repository<>));
services.DecorateWithLogging(); // 10.0.0: ArgumentException at startup
```

In 10.0.0 that combination threw an `ArgumentException` the moment the application started. The registration helper found the open registration and tried to build a closed decorator type from it with no type arguments.

Microsoft's container can't use a factory for an open generic, so the fix works with types instead. `DecorateWithLogging()` moves the original implementation to a keyed slot and registers the open generic decorator in its place with the same lifetime. The generated decorator for a generic interface now takes its inner instance with `[FromKeyedServices]`. Every closed form resolved from the open registration is logged, and closed registrations keep working exactly as before.

There is one limit. The keyed slot holds a single implementation, so only one open generic implementation per interface can be decorated. A second one makes `DecorateWithLogging()` throw an `InvalidOperationException` that names the interface and tells you to register the extra implementations with closed types. A clear message at startup beats silently decorating the wrong instance.

## Invalid input returns 400, not 500

`CoreDesign.ExceptionHandling` turns every exception nobody planned for into a generic 500, and that's the right default. ASP.NET Core's own `BadHttpRequestException` is different: it already knows the right status code. Minimal APIs throw it in `Development` when a route, query or body value can't be bound, and Kestrel throws it for problems such as an oversized request body.

In 10.0.0 the handler treated it like any other unexpected exception, so a request like `GET /WeatherForecasts/not-a-ulid` came back as a 500 with a stack trace. In 10.0.1 an unmapped `BadHttpRequestException` keeps its own status code:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "Bad Request",
  "status": 400,
  "detail": "Failed to bind parameter \"Ulid id\" from \"not-a-ulid\"."
}
```

The message appears in `detail` only in `Development`, the same rule the 500 fallback follows. A `[ProblemMapping]` for `BadHttpRequestException`, or for a subtype of it, still takes precedence.

## The generators need a current SDK

Both source generators now build against `Microsoft.CodeAnalysis.CSharp` 5.9.0. A generator can only load in a compiler at least as new as the one it was built against, so your build needs a .NET SDK whose compiler is Roslyn 5.9 or later. SDK 10.0.404 includes it. With an older SDK the compiler reports warning CS9057, the generators don't run, and `DecorateWithLogging()` and `AddGeneratedProblemMappings()` go missing. Run `dotnet --version` if you're not sure which SDK you have.

## Sample runs on 10.0.1

Until now the Sample application still referenced the 1.x packages, so it never exercised the current release. It now references 10.0.1, and its third-party dependencies are updated to match (ASP.NET Core 10.0.15, Aspire 13.6.5, OpenTelemetry 1.21.0). The full stack was verified end to end under Aspire with PostgreSQL: migrations and seeding, create, read, update and delete, the not-found paths, the new 400 response, and the deliberate unhandled exception.
