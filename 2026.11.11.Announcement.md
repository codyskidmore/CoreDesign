# CoreDesign, November 2026: .NET 11, C# 15 Unions, User Journey Tracking and an AI Skill

.NET 11 shipped this week, and CoreDesign 11.0.1 ships with it. Every package now targets .NET 11 and C# 15, and two changes lead the release. CoreDesign result types now work with unions built into the C# language, so you no longer need a third-party library to return "this value or that error" from a service. And a new package family, CoreDesign.UserJourney, lets you follow what each signed-in user viewed and did, from page views to clicks to data changes. There's also something new alongside the packages: a skill that teaches AI coding agents how to build with CoreDesign the way it's meant to be used.

A note on the version: 11.0.0 went out briefly before the user journey and configuration work below was finished. I withdrew it before anyone downloaded it, so 11.0.1 is the first .NET 11 release. Reference 11.0.1 or later.

Before the details: thank you. CoreDesign has now passed 10,000 downloads across its packages. When I wrote the July announcement it was closing in on 7,000. That growth is the main reason this release got the care it did, and it's why the breaking changes below come with a full upgrade guide.

This is the long-form write-up. A shorter note pointing back here will go out on LinkedIn.

## Do you need to upgrade?

No, not right away. The CoreDesign 1.x packages target .NET 10, and .NET 10 libraries run on the .NET 11 runtime. If you're on .NET 10 LTS, or you'd rather keep your code exactly as it is for now, stay where you are. Nothing breaks.

That said, this release is the line new CoreDesign features are built on, starting with the user journey packages below. They only ship for .NET 11, so plan the move when it suits you.

## From OneOf to C# 15 unions

CoreDesign has always encouraged services to return results instead of throwing for expected outcomes like "not found" or "bad request." Until now that meant `OneOf<...>`. C# 15 adds union types to the language, and `CoreDesign.Shared` now ships general-purpose unions that work the way OneOf did:

```csharp
// Before
Task<OneOf<Cabin, NotFoundMessage>> GetAsync(Ulid id, CancellationToken ct);

// After
Task<Union<Cabin, NotFoundMessage>> GetAsync(Ulid id, CancellationToken ct);
```

`Union<T0, T1>` through `Union<T0, T1, T2, T3>` live in `CoreDesign.Shared.Infrastructure`, next to `NotFoundMessage` and the other result records. Methods still return a case value directly, and the conversion to the union is implicit. Each union includes a `Match` method, so most existing code migrates with a rename and nothing else.

For new code I recommend a switch expression instead of `Match`, because the compiler checks it for you:

```csharp
var result = await service.GetAsync(id, ct);
return result switch
{
    Cabin cabin           => Results.Ok(cabin.ToResponse()),
    NotFoundMessage error => Results.NotFound(error.Message),
};
```

Add a third case to that union later and forget to handle it, and the build warns you (CS8509). OneOf could never do that; a missed case only showed up when it happened at runtime. That compile-time check is the real reason to make the switch.

There's also a new `Success` record for "it worked, there's nothing to return" results. Use `Union<Success, NotFoundMessage>` instead of `Union<bool, NotFoundMessage>`; a `bool` case gets boxed and says less about what happened.

You aren't limited to the generic unions, either. Declare your own and CoreDesign handles it the same way:

```csharp
public union CreateResult(WeatherForecast, BadRequestMessage);
```

## Why OneOf is no longer a dependency, and why your OneOf code still works

Previous versions of `CoreDesign.Logging` declared a NuGet dependency on OneOf, so installing Logging quietly installed OneOf too. When I went through it for this release, I found CoreDesign never actually used OneOf itself. The dependency was there for convenience. With unions in the language, carrying a third-party dependency that CoreDesign doesn't use no longer made sense, so it's gone.

What I did not want was to force anyone to rewrite working code to upgrade. So the `CoreDesign.Logging` source generator recognizes both:

- **C# 15 unions**, including `Union<>` and any union you declare yourself.
- **OneOf**, recognized by name, without CoreDesign referencing the OneOf package.

Either way, the generated logging decorators keep doing what they did before: a success case logs at Information, and error cases such as `NotFoundMessage` or `BadRequestMessage` log at Warning. You can migrate one method at a time, and OneOf and `Union<>` results can sit side by side in the same interface.

The one thing you may need to do: if your code uses OneOf but you never added it to your own project, the build fails with CS0246. One command fixes it:

```bash
dotnet add package OneOf
```

## New: follow each user's journey

This is the feature I'm most excited about. In my own production app, being able to pick a user and see exactly what they looked at and did, in order, changed how I support people and decide what to build. Products that do this charge a lot for it. CoreDesign.UserJourney does it with telemetry your app already sends.

```csharp
builder.Services.AddUserJourney();       // AddUserJourneyBlazor() for Blazor Server
builder.AddServiceDefaults();
// ...
app.UseAuthentication();
app.UseAuthorization();
app.UseUserJourney();
```

That's enough to link every request, page view and data change to the signed-in user, in Application Insights or any OpenTelemetry backend. A few more pieces fill in the rest:

- **Blazor Server clicks.** They travel over SignalR, not HTTP, so ordinary middleware never sees them. `CoreDesign.UserJourney.Blazor` links each circuit to its user and tags the clicks.
- **React and other single-page apps.** The new npm package `@coredesign.dev/user-journey` sends page views and clicks on elements you name with `data-journey` to an endpoint the API maps with one line, `app.MapUserJourneyEvents()`. It has no dependencies and comes in under 4 kB.
- **What a page showed.** `Journey.Viewed("Product", product.Name)`, or `<JourneyView>` in Blazor, records the item, so you can see which products a user looked at and not just which URLs.
- **A ready-made workbook.** Import it into Application Insights and pick a user to see their timeline, plus signed-in users per day, the most viewed pages, items viewed and the most common data changes.

Privacy was a design rule from the start. Only signed-in users get a journey, query strings are stripped, form values and typed text are never recorded, and email, name and IP can each be turned off. You should still tell your users about it in your privacy policy.

## New: a CoreDesign skill for AI coding agents

More and more code gets written with an AI agent in the loop, and an agent that has never seen CoreDesign guesses. It throws exceptions where a union belongs, hand-writes logging the source generator already provides, or writes migrations by hand. So this release includes a skill: a set of instructions and reference files that agents such as Claude Code load automatically whenever a task involves CoreDesign.

It covers every feature, step by step:

- **A complete solution from nothing:** the Aspire AppHost, an API with every package wired in, a migration service, the local identity server and a first feature with seed data.
- **Adding features** in the vertical slice style, with unions, generated logging, ProblemDetails mapping and permission checks.
- **User journey tracking** for APIs, Blazor and React.
- **Upgrading** from CoreDesign 1.x and OneOf.
- **The mistakes that show up in real projects,** each with the fix.

The setup guide isn't theory. I followed it from an empty folder on .NET 11 against the 11.0.1 packages: the solution builds, EF tooling creates the migration, the migration service migrates and seeds, and every endpoint, permission and error path returns what the guide says it will.

To use it with Claude Code, copy the `skills/coredesign` folder from the repository into `~/.claude/skills/` (or into a repository's `.claude/skills/` folder to share it with your team). The [skills README](https://github.com/codyskidmore/CoreDesign/tree/main/skills) has the details.

## Configuration improvements

A client project of mine ran into two limits in CoreDesign's configuration helpers, so this release fixes them:

- **Choose the settings file name.** `builder.AddAppSettings(o => o.SettingsName = "LOCAL")` loads `appsettings.LOCAL.json` while the environment stays `Development`, so settings files can follow your deployment names (LOCAL, DEV, UAT, PROD). The `AppSettings:Name` configuration value does the same without code, and the file actually loaded is logged at startup.
- **Environment variables win again.** `AddAppSettings` used to add its JSON files after every other configuration source, so they overrode App Service settings, Docker environment variables and user secrets. That's backwards from how .NET configuration normally works, and it's fixed. It's a behavior change, so it's listed under breaking changes below.
- **Explicit local token injection.** CoreDesign.Identity.Client signs local tool requests in as a development user, and until now only the environment name decided that. `IdentityApi:EnableLocalTokenInjection` makes it an explicit setting: `true` locally, `false` everywhere else. Unset, nothing changes.
- **Private address helpers.** `IsPrivate()` and `IsInternal()` on `IPAddress` replace the hand-written range checks APIs use to exempt internal callers from rate limiting.

## Breaking changes

All of these are covered step by step in the [upgrade guide](https://github.com/codyskidmore/CoreDesign/blob/main/CoreDesign.NET11-migration.md):

- **Every package targets `net11.0` only.** Move your projects to .NET 11 and the .NET 11 SDK.
- **`CoreDesign.Logging` no longer brings in OneOf.** Add your own reference if you use it.
- **`CoreDesign.Shared` adds `Success`.** A file that imports both `OneOf.Types` and `CoreDesign.Shared.Infrastructure` and mentions `Success` reports an ambiguous reference (CS0104). Remove one `using` or alias it.
- **`CoreDesign.Identity.Client` requires `Microsoft.OpenApi` 3.x**, because ASP.NET Core 11's OpenAPI support requires it. If you pin `Microsoft.OpenApi` 2.x, restore fails with NU1605 until you move to 3.x.
- **The `dotnet seed` tool needs the .NET 11 runtime.**
- **Environment variables, user secrets and command-line arguments now override `AddAppSettings` files.** Before, the JSON files won. If a deployed environment sets the same key in both places, the environment variable now wins; remove whichever value should no longer apply.

You'll also see NU1510 warnings if your projects reference `Microsoft.Extensions.*.Abstractions` packages. .NET 11 moved nine of them into the base framework, so the references are redundant. Remove them; CoreDesign already has.

## Security and dependency updates

- **Aspire 13.4.6 to 13.6.5.** Microsoft published CVE-2026-120006, a high severity elevation of privilege issue in Aspire hosting, the day .NET 11 shipped. `CoreDesign.Shared` depends on Aspire hosting, so this release moves it to the fixed version. Update your own Aspire packages and AppHost SDK to 13.6.5 too.
- **MessagePack 3.1.12**, which fixes GHSA-qhrr-8q5h-9q3h.
- **Microsoft ASP.NET Core and `Microsoft.Extensions.*` packages** move to 11.0.0.

One thing that didn't move: **EF Core stays on 10.0.x** in this release. The PostgreSQL provider for EF Core 11 hasn't reached a stable release yet, and EF Core 11 can't run with the current PostgreSQL provider. EF Core 10 runs fine on .NET 11. If you're on SQL Server and want EF Core 11 today, reference it in your own project and NuGet picks the higher version. CoreDesign.Data will move to EF Core 11 in a follow-up release once the PostgreSQL provider is stable.

## How this was tested

Unit tests are necessary but not enough for a change this wide, so I don't ship a CoreDesign release until a real application runs on the exact packages. For this release that's a production application that uses every CoreDesign package. Its migration replaced OneOf in more than 400 places, and its generated logging decorators produced exactly the same per-case logging before and after the move to unions. The user journey packages come from code that has run in that application's production since early November; it now uses the packages in place of its own code. It passes its full test suite of over 1,000 tests and runs cleanly on .NET 11.

## New version numbers

You'll notice the versions jump from 1.x to 11.0.1. Until now each package had its own version number, so it was never obvious which Logging version went with which Data version, or which .NET version either one needed. Starting with this release, every CoreDesign package shares one version, and the major version matches .NET: CoreDesign 11 is for .NET 11.

That comes with a promise. Minor and patch releases, such as 11.1.0 or 11.0.2, will never break your code. Breaking changes wait for the next .NET release each November, and anything being removed gets marked obsolete first, so you see the warning before it's gone.

## Get started

Add the packages your project needs:

```bash
dotnet add package CoreDesign.Shared
dotnet add package CoreDesign.Logging
dotnet add package CoreDesign.UserJourney
```

For a React front end:

```bash
npm install @coredesign.dev/user-journey
```

In PowerShell, put the npm package name in quotes (`"@coredesign.dev/user-journey"`), because PowerShell treats a leading `@` as an operator.

The [user guide](https://github.com/codyskidmore/CoreDesign/blob/main/CoreDesignUserGuide.md) covers every package, and the [release notes](https://github.com/codyskidmore/CoreDesign/blob/main/RELEASE_NOTES.md) list every change.
