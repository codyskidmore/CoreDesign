# CoreDesign, July 16 2026: Dependency Refresh and a Rethink on PurgeBeforeSeed

I'm pushing out a new round of CoreDesign packages today. Before anything else: thank you. CoreDesign is closing in on 7,000 downloads across its packages, and every one of those represents someone deciding this was worth pulling into their project. I did not expect that when I started this, and I'm genuinely humbled by it.

This post is the long-form version of what's changing. A shorter note pointing back here will go out on LinkedIn, since the full write-up doesn't fit that format well.

## This is not a critical release

Nothing in this release fixes a security vulnerability or a data-loss bug. There's no urgency here. If you're on the current versions and things are working, you can take this update whenever it's convenient, or skip it for a cycle. The bulk of what follows is routine dependency maintenance, plus one behavioral refinement to `PurgeBeforeSeed` in `CoreDesign.Data` that I want to explain in detail, including the part I haven't fully settled on yet.

## Dependency updates

Microsoft shipped its usual monthly patch releases, and the .NET/Aspire ecosystem moved forward with it. Nothing here was prompted by a known CVE; it's just keeping current so a real vulnerability, when one does show up, lands on a codebase that's already close to the latest patch line instead of several releases behind.

There is no API surface change from any of them. If you already track Microsoft's release cadence in your own projects, none of this will be a surprise.

## PurgeBeforeSeed: a safety refinement, and where I'm still undecided

`PurgeBeforeSeed` is a feature in `MigrationWorker` (part of `CoreDesign.Data`) that lets you clear a table before its seed file is reapplied, so you can replace seed content wholesale on a run instead of only ever filling in gaps. The default behavior, insert rows that don't already exist by primary key and leave everything else alone, hasn't changed. It's still what happens automatically with no configuration at all.

What changed is how the tool treats the destructive path. `PurgeBeforeSeed` clears the entire table, unrecoverably outside of a database backup, and the previous version logged that at `Information` level with no particular warning attached. That's too quiet for something this destructive. In this release:

- Purging now logs at `Warning` level, with an explicit message stating that the operation is destructive and must never be enabled against a Production database.
- The XML documentation on `MigrationWorker`, `AddMigrationWorker`, and the purge method itself all carry the same caution language.
- The documented workflow in the `CoreDesign.SeedTool` README and the CoreDesign user guide, which previously described adding an entity to `PurgeBeforeSeed` and then deploying as the normal way to push updated content, has been corrected. That workflow is scoped to non-Production environments now: local development or a staging database while you iterate toward a final seed data set. Production content changes remain something an administrator does directly against the database, not something a redeploy does for you.
- This is covered by tests now, including one that specifically asserts the warning log fires with the expected message, so a future change can't silently soften this back down without a test failing.

Here's the part I want to be upfront about: I'm not fully settled on whether a warning is the right level of guardrail for this. Right now, `PurgeBeforeSeed` is a warning and a documentation note, nothing technical stops it from being configured for a Production database if someone puts the entity name in `appsettings.Production.json`. I went back and forth on whether it should instead be a hard gate, something that refuses to purge at all when `IHostEnvironment.IsProduction()` is true, or that requires a second, explicit opt-in flag before it will run anywhere. I chose the lighter-weight approach for this release because a hard environment-based gate has its own failure mode: it depends on `ASPNETCORE_ENVIRONMENT` being set correctly, and a misconfigured environment variable could either block someone who legitimately needs it in a Production-like staging tier, or worse, create a false sense of safety if the check is wrong somewhere.

I don't think I've landed on the right answer yet, and I'd like to hear from people actually using this feature. If you have an opinion on warning versus hard block, or a middle ground I haven't considered, open an issue at [github.com/codyskidmore/CoreDesign/issues](https://github.com/codyskidmore/CoreDesign/issues). This is exactly the kind of design decision that benefits from more than one perspective, and I'd rather get it right before it's load-bearing for more people's deployment pipelines.
