# CoreDesign.Logging 1.0: Problems Solved by the 1.1.0 Generator

This document catalogs every known problem with the `DispatchProxy`-based `LoggingMiddleware<T>` that shipped in versions 1.0.x. It is the record behind the decision to build the 1.1.0 source generator.

Some of these problems were patched in 1.0.5. Those patches are noted. In every case the patch was a workaround inside the proxy; the generator eliminates the underlying cause.

---

## 1. Circular Reference Serialization Crash

**What happened.** `LoggingMiddleware` serialized return values to JSON using `System.Text.Json.JsonSerializer`. Entity objects with navigation properties (a `WeatherForecast` that holds a reference to a `Location` that holds a reference back to a list of `WeatherForecast` objects) caused `JsonSerializer` to throw a `JsonException`. That exception escaped the logging path and broke the method call entirely.

**1.0.5 patch.** `ReferenceHandler.IgnoreCycles` was added to the serializer options. Circular back-references are written as `null` rather than throwing.

**Why the generator eliminates it.** The generator does not serialize anything. It passes parameters and return values to the structured logging provider using `{@notation}`, which instructs the provider to destructure the object using its own pipeline. The provider (Serilog, etc.) handles cycles through its own policies. There is no `JsonSerializer` call in any generated decorator.

---

## 2. OutOfMemoryException from Deeply Nested Objects

**What happened.** Deeply nested objects (recursive tree structures, heavily composed DTOs, EF Core entity graphs with many levels of navigation) caused the JSON serializer to generate extremely large strings. In the worst cases this caused `OutOfMemoryException`. Even when it did not throw, the resulting log entry was too large to be useful.

**1.0.5 patch.** `MaxDepth = 8` was set on the `Utf8JsonWriter`. Serialization stops at depth 8, and the log suffix changes to indicate the truncation. The limit is arbitrary and hard-coded in the proxy source.

**Why the generator eliminates it.** Serilog's `Destructure` configuration controls object graph depth, string length, and collection size uniformly across all decorated methods and all sinks. The critical setting is `ToMaximumDepth`: without it, Serilog will follow every object reference in a deep graph until the payload is exhausted, which causes the application to hang while the log streams out. Testing confirmed that this hang occurs without `ToMaximumDepth` even after the circular reference and memory exceptions are resolved, the application stops throwing but starts hanging instead. All limits are configuration values, not constants in source code, and can be adjusted per environment without a code change or rebuild.

## 3. Fragile Async Return Type Handling

**What happened.** `DispatchProxy` intercepts calls as untyped `MethodInfo.Invoke` returns. When the actual return type was `Task<T>`, the proxy had to inspect the `Type` object at runtime and call `MakeGenericMethod` to construct and await the right wrapper. This logic (`WrapTask`/`WrapGenericTaskAsync`) was the most fragile part of the entire implementation:

- Hard to step through in a debugger.
- Produced extra stack frames in every exception trace.
- Would silently break if a method returned an unconventional awaitable type the runtime type check did not anticipate.
- Had no compiler feedback if the wrapping logic was wrong.

**Why the generator eliminates it.** The generator inspects return types at build time, not at runtime. The emitted code is a plain `await` expression. There is no `MakeGenericMethod`, no runtime type inspection, and no wrapper construction. If the emitted code is wrong the compiler says so immediately.

---

## 4. Reflection Overhead on Every Method Call

**What happened.** Every single method call on a proxy-wrapped service went through `MethodInfo.Invoke`. Reflection-based dispatch is measurably slower than a direct method call, typically by a factor of 10x to 100x depending on the CLR version and argument count. For services on a hot path (handlers called on every HTTP request, repositories used in loops) this overhead accumulates.

**Why the generator eliminates it.** Generated decorators are sealed classes with direct method calls. The compiler generates the same CIL as a hand-written decorator. There is zero reflection at runtime.

---

## 5. .NET Native AOT Incompatibility

**What happened.** `DispatchProxy.Create<T, TProxy>()` generates a new class at runtime using the CLR's dynamic code generation facilities. .NET Native AOT compiles the application to a self-contained native binary before execution and does not include the CLR's code generation infrastructure. Any project that targeted AOT with the proxy in the dependency chain would fail at publish time or silently at runtime.

**Why the generator eliminates it.** Generated decorators are ordinary C# classes written out to source files at build time. There is no runtime code generation, no `DispatchProxy`, no `MakeGenericMethod`, and no reflection of any kind. They are fully AOT-safe.

---

## 6. Noisy Exception Stack Traces

**What happened.** When a service method threw an exception, the stack trace shown in logs and debuggers included frames from inside the reflection dispatch: `MethodInfo.Invoke`, `RuntimeMethodHandle.InvokeMethod`, and several internal CLR frames. These frames appear before the application code in the trace, making it harder to identify the actual source of the exception and adding noise to error reports.

**Why the generator eliminates it.** Generated decorators call methods directly. An exception thrown by the inner implementation propagates through a single `catch` block in the decorator and then to the caller. The stack trace contains only frames that belong to the application.

---

## 7. No Compile-Time Interface Enforcement

**What happened.** The proxy intercepted calls dynamically at runtime. If a method was added to an interface and the implementation was updated, the proxy would log it correctly, but nothing verified that the proxy's own logic handled the new signature correctly. If the attribute configuration had gaps or the proxy had a bug that affected only certain return type shapes, the failure appeared at runtime under load, not at build time.

More practically: the proxy registered services by interface, but there was no compile-time check that the registered implementation actually matched the interface. Type mismatches became runtime exceptions.

**Why the generator eliminates it.** Each generated decorator is a C# class that explicitly implements the interface. If the interface gains a method, the generated decorator gains the corresponding method on the next build. If for any reason the generated output did not match (wrong return type, missing parameter), the compiler would refuse to build. The error appears before the application runs.

## 8. `ILoggable` Couples Implementation Classes to Logging Infrastructure

**What happened.** To opt a class into automatic logging registration, the implementation had to implement the `ILoggable` marker interface:

```csharp
public class CreateForecastHandler(...) : ICreateForecastHandler, ILoggable { }
```

`ILoggable` carries no members. Its sole purpose is to tell the logging infrastructure to wrap the class. That is an infrastructure concern, and it has no place on a domain handler or application service. The class now has a dependency on `CoreDesign.Logging` even though nothing in its logic uses logging.

**Why the generator eliminates it.** `[LoggingDecorator]` is placed on the interface, not the implementation. The implementation remains free of any logging attribute, marker, or import. The logging concern is confined to the contract definition, which is the correct place for cross-cutting policy.

---

## 9. `[TruncateLog]` Scatters Infrastructure Configuration Across Interface Files

**What happened.** Controlling how much of a return value was written to the log required adding `[TruncateLog]` to each method individually:

```csharp
[TruncateLog(2000)]
Task<IReadOnlyList<WeatherForecast>> GetAllAsync(CancellationToken ct);
```

This meant:
- Infrastructure policy (log truncation) was encoded in interface files alongside business contracts.
- Changing a limit required finding the right interface file, editing it, committing, and deploying.
- Different methods could have different limits, and there was no single place to audit what limits were in effect.
- Methods that should have had the attribute but did not used the default silently.

**Why the generator eliminates it.** The generator does not support `[TruncateLog]`. Output size is controlled by Serilog's `Destructure` configuration in `appsettings.json`. The limit is in one place, applies to every decorated method and every sink, and does not require any change to the interface or a rebuild to adjust.

---

## 10. Log Output Limits Are Hard-Coded in Source

**What happened.** Beyond `[TruncateLog]`, the default truncation limit (500 characters) and the depth cap (8 levels, added in 1.0.5) were constants in the proxy source code. Adjusting them required modifying `LoggingMiddleware.cs`, rebuilding the package, updating the package reference in every consuming project, and redeploying.

**Why the generator eliminates it.** There are no hard-coded limits in any generated class. Limits are Serilog configuration values. Raising the limit for a debugging session means editing `appsettings.Development.json`. No source change, no rebuild, no package update.

---

## 11. Properties and Indexers Logged as Method Invocations

**What happened.** `DispatchProxy` intercepts all method calls on the interface, including the `get_PropertyName` and `set_PropertyName` accessor methods that back C# properties and indexers. Any interface that declared a property or indexer would have every read and write logged as if it were an ordinary method call. For a property like `int Count { get; }`, every access produced an `Invoking Count` log entry. This was noise that obscured the method-level signal the proxy was intended to produce.

**Why the generator eliminates it.** The generator inspects each interface member and handles properties separately from methods. Properties and indexers are emitted as plain pass-throughs with no log calls. Only methods marked as `MethodKind.Ordinary` produce log entries.

---

## 12. Generic Interface Support Is Not Workable

**What happened.** `AddWithLogging(assembly)` scanned for classes implementing `ILoggable` and paired each class with its non-marker interfaces. For a generic interface such as `IRepository<T>`, the scan would encounter a specific closed instantiation (e.g., `IRepository<WeatherForecast>`) but had no generalized way to register all concrete uses under a single policy. Open-generic registration was not supported by the proxy registration machinery.

**Why the generator eliminates it.** The generator inspects the interface at build time and emits a generic decorator class with the same type parameters and constraint clauses:

```csharp
public sealed class RepositoryLoggingDecorator<T> : IRepository<T> where T : class { ... }
```

`DecorateWithLogging()` registers this using open-generic DI: `Decorate(services, typeof(IRepository<>), typeof(RepositoryLoggingDecorator<>))`. Every concrete registration of `IRepository<T>` (regardless of what `T` is) is wrapped automatically.

---

## 13. Return Values Are Pre-Serialized Strings, Not Structured Data

**What happened.** The proxy converted return values to JSON strings before passing them to `_logger.LogInformation`. The logging provider received a flat string:

```
CreateAsync returned {"Id":"abc","Temperature":72,"Summary":"Warm"}
```

Because the value had already been serialized, structured logging providers such as Serilog, Application Insights, and Seq could not further destructure or index it. Queries against individual fields in a log aggregator were not possible. The string was opaque from the provider's perspective.

**Why the generator eliminates it.** Generated decorators use structured logging notation:

```csharp
_logger.LogInformation("{Method} returned {@Result}", "CreateAsync", result);
```

The `@` prefix tells the provider to destructure `result` using its own pipeline. Serilog stores the individual properties of the return value as structured fields. Seq and other sinks can query against `Result.Id`, `Result.Temperature`, and so on. The full power of structured logging is available.
